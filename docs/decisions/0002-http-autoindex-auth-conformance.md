# ADR 0002 conformance vectors: HTTP and registry authentication

These vectors translate [ADR 0002](0002-http-autoindex-auth-contract.md) into black-box tests. Paths, credentials, and registry contents below are test data. The secure mount `M1` uses prefix `/pkg`, registry origin `https://reg-a.example`, repository `team/a`, root tag `tree-a`; `M2` uses `/mirror`, `https://reg-b.example`, `team/b`, `tree-b`. Unless a vector overrides it, requests use a trusted HTTPS client connection. `R` is the received response from the HTTP service. “No registry call” means the recording registry's request counter is unchanged.

Tests distinguish three credential contexts:

1. **Caller credential:** the exact incoming HTTP `Authorization` field sent to the service.
2. **Registry credential:** that same field, if present, forwarded to the selected registry origin.
3. **Realm credential/token:** a value the client's platform may obtain directly from a `WWW-Authenticate` realm and use on a later request. The service MUST NOT contact the realm to obtain or exchange it.

In conditional vectors, `<etag>` means the exact quoted strong ETag observed from the preceding file response. Use a recording/auth-configured registry for exact outbound-header assertions and a real OCI Distribution-compatible registry with authentication for end-to-end checks. Recording fixtures MUST capture headers in memory without writing credential values to logs. The real registry tests MUST use disposable sentinel credentials.

| ID | Request/setup | Expected client-facing response | Required upstream/security assertion |
| --- | --- | --- | --- |
| ANON-1 | `GET /pkg/readme.txt` with no `Authorization`; registry permits anonymous blob reads. | `200`, exact bytes, `text/plain; charset=utf-8`, digest ETag, exact `Content-Length`, `Accept-Ranges: bytes`, `Cache-Control: private, no-store`. | Requests to `reg-a.example` contain no `Authorization`; no application login is requested. No request reaches `reg-b.example`. |
| BASIC-1 | `GET /pkg/file.bin` with `Authorization: Basic dGVzdDpzZWNyZXQ=`; registry is configured to accept only that exact Basic value. | Accepted credential returns `200` and exact file bytes. A different Basic value is rejected by the registry and its challenge/status are handled by AUTH-1/REJECT-1. | `reg-a.example` receives the exact field value once per OCI request; the service does not decode/re-encode it, use another credential, or send it to `reg-b.example`. The value is absent from logs, traces, errors, and response body. |
| BEARER-1 | First request has no `Authorization`; registry returns `401` with `WWW-Authenticate: Bearer realm="https://auth.example/token",service="reg-a",scope="repository:team/a:pull"`. The test client obtains a sentinel realm token directly from `auth.example`, then retries with `Authorization: Bearer test-issued-token`. Separately, test `Bearer realm="example"` as an opaque realm identifier. | First response is `401` with the exact challenge value and no registry error body. Retry returns the file when the registry accepts that token; opaque realm challenge is also relayed unchanged. | The service does not call `auth.example`, parse the challenge into a login, or mint/exchange a token. First registry request has no Authorization; retry registry requests receive exactly `Bearer test-issued-token`. The token is not stored or logged. Absolute URL realms must be HTTPS; opaque identifiers remain opaque. |
| REJECT-1 | Retry `GET /pkg/file.bin` using `Authorization: Bearer invalid-test-token`; registry rejects it with `401` and one or more challenges. | `401`; all valid `WWW-Authenticate` fields appear with the same values and order; generic body; `Cache-Control: private, no-store`; `Vary: Authorization`. | The service forwards the invalid value unchanged to `reg-a.example`, does not invent a separate challenge, does not relay upstream error body/`Set-Cookie`, and does not send the value to another origin. |
| CHALLENGE-1 | Registry returns multiple valid `WWW-Authenticate` field instances (for example Basic and Bearer), including quoted commas. In separate cases return `Bearer realm="https://auth.example/token",broken="unterminated` and `Bearer realm="https://auth.example/token%"`. | Valid fields produce `401` and preserve each field value and field order exactly; no challenge is folded, parsed/reconstructed, or lost. The unterminated quoted-string and malformed URL percent-escape return generic `502` with no challenge header. | Only the configured HTTPS registry's fully parseable RFC 9110 challenge is relayed. A Bearer realm using HTTP or invalid URL syntax, a challenge from an unapproved redirect host, or a challenge that would reach a cleartext client produces the ADR's generic `502`/`403` result with no challenge leakage. |
| MOUNT-1 | Configure disjoint `/pkg` and `/pkg-old`; request `/pkg-old/item`, `/pkg/item`, `/pkg-old`, and `/pkg-oldish/item`. Separately try overlapping `/pkg` and `/pkg/sub`. | Each request reaches only the exact segment-boundary mount; `/pkg-oldish/item` is `404`. Overlapping mount configuration fails before listening. | Each upstream request is restricted to the one selected registry/repository/root tag; there is no fallback from a missing object in one tree to another. No overlapping configuration starts the listener. |
| PATH-1 | Request `/pkg/a%2Fb`, `/pkg/%2e%2e/secret`, `/pkg/a//b`, `/pkg/%`, an over-limit path, and a path containing an encoded backslash. | Every request returns `400`; error body is generic. | No registry is contacted and no tree is changed. Malformed paths never become registry hosts, repositories, tags, or object names. |
| INDEX-1 | Seed root children: directory `b/`, file `a&b.txt`, file `<script>.txt`, and file `z.txt`; request `GET /pkg/` with `Host: attacker.example` and query `?token=do-not-log`. | `200`, UTF-8 HTML. Parent link is absent at the root. Directory `b/` appears before files; files follow unsigned UTF-8 order. Text uses `&amp;` and `&lt;`; hrefs are `/pkg/a%26b.txt`, `/pkg/%3Cscript%3E.txt`, `/pkg/z.txt`, and `/pkg/b/`. Response has `Content-Security-Policy`, `Referrer-Policy`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, and `Vary: Accept, Authorization`; no script or `attacker.example` appears. | Query is not sent upstream or logged. HTML is generated from one pinned tree snapshot. No `Access-Control-Allow-*` header is emitted. |
| INDEX-2 | Request `/pkg` and `/pkg/b` where `b` is a directory; request `/pkg/b/` where `b` is a file; request `/pkg/missing/`; request a known directory with `Accept: application/json`. | Directory paths without slash return `301` with canonical encoded `Location` and no query. A file with slash and missing path return generic `404`. JSON-only `Accept` on a directory returns `406`. | No path crosses mount boundaries; the HTTP service does not implicitly serve `index.html`. |
| METHODS-1 | Send `POST`, `PUT`, `DELETE`, and `OPTIONS` to a valid mounted path. | Each returns `405` with `Allow: GET, HEAD`. | No registry calls occur. |
| FILE-1 | Read a `.TXT` file with `GET`, then `HEAD`; seed a file named `index.html` and request its containing directory. In a separate fixture, keep correct blob HEAD metadata but corrupt the blob body. | `GET` returns bytes with `text/plain; charset=utf-8`, strong ETag, exact size, and no `Last-Modified`. `HEAD` has matching path/metadata-derived status and headers, no body, and a registry blob `HEAD` check. For the corrupt-body fixture, `HEAD` may be `200` while `GET` is `502`, as explicitly allowed by the contract. The directory still renders autoindex; only `/pkg/.../index.html` serves that file. | A caller's `Accept` does not change file representation. `HEAD` verifies referenced blob availability/size without downloading body bytes and cannot detect a body digest mismatch; `GET` verifies the complete digest. |
| RANGE-1 | For bytes `0123456789`, request `Range: bytes=2-5`; repeat with `bytes=20-` (valid but unsatisfiable), `bytes=3-2` (malformed reversed interval), `bytes=0-1,4-5`, and a nonmatching `If-Range`. | `bytes=2-5` returns `206`, `Content-Range: bytes 2-5/10`, length 4, body `2345`. `bytes=20-` returns `416`, `Content-Range: bytes */10`. The malformed `bytes=3-2`, multiple range, and nonmatching `If-Range` return full `200`. | Successful `GET` validates the entire blob digest and size before releasing the final response byte; memory use stays bounded. `HEAD` never returns a body. |
| CONDITIONAL-1 | Obtain a file ETag. Retry with matching `If-None-Match`; with nonmatching `If-Match`; then with matching strong `If-Range` and a satisfiable Range. | Matching `If-None-Match` gives `304` with no body. Nonmatching `If-Match` gives `412`. Matching `If-Range` allows `206`. Date conditionals are ignored because no `Last-Modified` exists. | ETag is derived from the layer SHA-256 digest; these outcomes do not invoke an application login or alter the tree. |
| CONDITIONAL-2 | Send `If-Match: "wrong"` with an unsatisfiable `Range: bytes=20-`; then send matching `If-Match: <etag>` and matching `If-None-Match: <etag>` with that same range; finally use matching `If-Match`, nonmatching `If-None-Match`, and the unsatisfiable range. | Responses are respectively `412`, `304`, and `416`, proving preconditions run before Range and `If-Match` precedes `If-None-Match`. | No file content is returned for 412/304/416. The evaluated validator is the ETag derived from the indexed layer digest. |
| TRANSPORT-1 | Send a request carrying `Authorization` over an untrusted cleartext connection. Separately configure an explicitly insecure anonymous registry that returns `401`. | Cleartext credential request returns `403`; insecure registry challenge returns `502` without `WWW-Authenticate`. | Neither credential is sent over plaintext; insecure registry mode never relays auth challenges or enables credential pass-through. |
| REDIRECT-1 | Registry returns same-origin HTTPS blob redirect, then an allowlisted cross-origin HTTPS CDN redirect, then an unallowlisted host/HTTP downgrade redirect. | Allowed redirects return the correct file response. Unapproved/downgrade redirects return generic `502`. A `401` from a redirect destination is not exposed as the registry challenge. | Same-origin configured-registry requests may retain Authorization. Every cross-origin hop strips Authorization and other sensitive fields. The CDN is contacted only when explicitly allowlisted; unapproved targets are never contacted. |
| ERRORS-1 | After successful startup, remove the root tag; also exercise missing path, missing referenced blob, malformed reachable index, registry `429` with `Retry-After`, and registry timeout. | Missing path is `404`; unavailable/uninitialized root is `503`; missing referenced blob or corrupt tree is generic `502`; rate limit is `503` with only a valid `Retry-After`; timeout is `504`. A missing root tag at startup instead fails readiness. | Error bodies do not expose registry URLs, repository names, credentials, upstream bodies, or query strings. Integrity errors are logged without secrets. |
| RETRY-1 | Have the registry return `429` with `Retry-After: 120`, then with `Retry-After: Wed, 21 Oct 2015 07:28:00 GMT`, then with `Retry-After: soon`. | Every response is `503`. The first two relay the exact valid value; the invalid value is omitted. | Validation follows RFC 9110 §10.2.3 delay-seconds/HTTP-date syntax; no upstream body or other header is relayed. |
| REDACT-1 | Send a sentinel credential and a query containing `token=sentinel-query`; induce registry `401`, `403`, `429`, timeout, and malformed-manifest errors. Inspect configured logs/traces and every response. | No response body or ordinary response header contains the sentinel credential/query. A valid `WWW-Authenticate` is the only upstream challenge value intentionally relayed. | Neither sentinel appears in access/error logs, tracing spans, metrics labels, panic reports, or persistent OCI metadata. Query strings and signed upstream redirect URLs are redacted/omitted from logs. |

## Test execution notes

Run the auth vectors against an authenticated real OCI Distribution registry in addition to a header-recording fixture; the fixture alone cannot establish registry credential acceptance. Keep the caller token, realm token, and registry-side observations separately labeled in test output, and print only pass/fail plus redacted digests. For REDIRECT-1, use controlled same-origin and CDN-like endpoints with an explicit allowlist. For PATH-1 and METHODS-1, assert the registry request counter remains unchanged. For file integrity/range tests, inject a wrong digest or short blob and verify that no response completes with the declared successful content length.
